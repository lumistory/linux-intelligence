# Security boundary — v0

Status: **draft**, derived from the measurements in
`experiments/00-g-privilege/REPORT.md`. Every rule below cites the measurement
that justifies it. Where a rule is a design choice rather than a measurement,
it says so.

This document defines: what we trust, how we identify a caller, what an
interface may accept, what we must log, and what we deliberately refuse to build.

---

## 1. Trust boundary

### 1.1 What exists

| component | privilege | trust |
|---|---|---|
| **User daemon** (Phase 1+) | the invoking user's uid, nothing more | trusted to act for that user, not trusted with other users' data |
| **Recorder / adapters** (shell hooks, pty, proc, fs) | same uid | **untrusted input**: a shell hook can fire twice or lie |
| **Privileged helper** (Phase 3+, conditional) | whatever it was granted | trusted only to the extent §5 constrains it |
| **unprivileged peer** (any process of the same uid) | same uid | **untrusted input**, even though it is "the same user" |

### 1.2 The boundary itself

The boundary is drawn at **uid verification plus a data-only interface**, not at
a privileged/non-privileged line.

Rationale, measured: a user namespace gives uid 0 with the *full* capability
set (`CapEff: 000001ffffffffff`) and still cannot read `/etc/shadow`
(`DENIED Permission denied`, `T2-userns-root`), cannot list `/root`, cannot
signal host pid 1 (`DENIED Operation not permitted`), and creates files that the
host sees as `uid=1000 gid=1000`. Its `CAP_DAC_OVERRIDE` reaches exactly the
inodes owned by **mapped** uids — that is, exactly what the user already had.

**Therefore: namespace root ≠ host root, and a user namespace can never
substitute for real privilege.** Any claim that a feature "works because it runs
in a namespace" is a claim that it needs no privilege at all.

### 1.3 Same-uid peers are not trusted

An `AF_UNIX` socket in `$XDG_RUNTIME_DIR` is reachable by every process of the
same uid. Those processes may be compromised, may be a different program than
expected, and may lie about who they are. The daemon must validate every frame
as if it came from an attacker — because in the only threat model that matters,
it did.

Cross-uid callers are blocked by two independent gates, both measured
(`T3b-unauthorized-uid`):

1. **Kernel gate** — socket mode `0600` inside a `0700` directory. A uid-5
   `connect()` gets `EACCES` before the server runs.
2. **Application gate** — the `SO_PEERCRED` uid allowlist. With the kernel gate
   deliberately opened (`parent 0777`, `socket 0666`) the peer connects and is
   still refused: `{"code":"not_authorized","message":"peer uid not allowed"}`.

Neither gate alone is sufficient. The kernel gate is a configuration that can be
changed by a later `chmod`; the application gate is code that can be reviewed.

## 2. Identity verification

### 2.1 The three fields, and what each is worth

| field | source | usable for authorisation? | why |
|---|---|---|---|
| `uid` | `SO_PEERCRED` | **YES** | enforced by the kernel at `connect()`; not recycled to another user |
| `gid` | `SO_PEERCRED` | informational | supplementary groups are not in the credential |
| `pid` | `SO_PEERCRED` | **NO** | a frozen snapshot; the pid may already belong to another process |
| `starttime` | `/proc/<pid>/stat` field 22 | attribution only | 10 ms granularity; collides within a tick |

### 2.2 Why `pid` is forbidden as an authorisation key

Measured, `T1-peercred`:

- `cred_is_frozen: true` — the credential returned after a 1 000 245 131 ns
  delay is byte-identical to the one read at `accept()`. It is a snapshot, not a
  lookup.
- After the server reaps the client, `liveness_after_reap: "gone"`
  **while the socket is still open and still reports that pid**.
- With a forced reuse, a different process takes the freed pid and the same
  socket's credential now names it:
  `cred_pid_now_names_the_impostor: true`,
  `naive_pid_only_identity_confusion: true`.

A server that reads `SO_PEERCRED` late and then opens `/proc/<pid>` to make a
decision is reading a file about a **different process**.

### 2.3 The triple `uid + pid + starttime`

This is the recommended **attribution** record. It is what an audit line should
contain so a human can later answer "which process was this".

It is **not** an authorisation mechanism, and the measurement is unambiguous:

```
clk_tck=100, trials=20, forks_at_target_pid=20, collisions=20
verdict: pid_starttime_is_not_a_unique_key_within_one_tick
```

In 20 of 20 forced-reuse trials, two distinct processes inside one 10 ms tick
shared both `pid` and `starttime`. In
normal operation the pair does separate reuse (the impostor test shows
`starttime_differs_from_client: true` for reuse 150 ms later), so the pair is
*good evidence* and *bad proof*.

### 2.4 What to authorise on instead

Authorise on **`uid` + a per-connection capability generated by the server**:

1. On accept, read `SO_PEERCRED`. Refuse unless `uid` is in the allowlist.
2. Mint a random per-connection token; bind it server-side to that connection.
3. Every authorisation decision uses the token and the connection's own state.
   Never re-read `SO_PEERCRED`. Never touch `/proc` for a decision.
4. Record `uid + pid + starttime + token` in the audit line for attribution.

The token is the load-bearing identity. `pid` and `starttime` are evidence
attached to it, and if they disagree with the token, the token wins and the
disagreement is logged as an anomaly.

**Status: designed, NOT TESTED.** No measurement in 0-G exercises a
capability token. This is the highest-priority gap in this document (§6.2).

## 3. Interface whitelist principles

### 3.1 The interface accepts data, not commands

Every request is `{opcode: integer, args: object}`. There is:

- **no field** that names a program, shell, interpreter, script, or syscall;
- **no field** whose value is evaluated, expanded, or templated;
- **no opcode** whose effect is "run", "eval", "open arbitrary path" or
  "write arbitrary path".

Measured, `T6-no-exec`: a battery of 12 hostile requests (shell metacharacters,
`$(...)`, backticks, pipes, `nc -e`, string opcodes, `"argv":["id"]`, absolute
paths, oversized arguments) produced **zero** `execve` after the helper's own
startup:

```
execve_lines_total=1
execve_lines_of_the_helper_binary=1
execve_lines_after_startup=0
```

### 3.2 Opcodes are a closed numeric set

- Numeric only. `{"opcode":"exec"}` is `bad_opcode`, a *typed* refusal, not a
  lookup miss — it appears in the audit log rather than being coerced.
- Negative, fractional, string, array: all `bad_opcode`.
- Unknown integers: `unknown_opcode`.
- Recognised-but-refused opcodes (e.g. `BtrfsSnapshot`) return
  `not_implemented_by_design`, so "we chose not to" is distinguishable from
  "we did not recognise it".
- Adding an opcode is a protocol change, not a configuration change.

### 3.3 Arguments are a strict per-opcode allowlist

Undeclared keys are an error (`arg_unexpected`), not ignored.

This is not pedantry. Before the check existed,
`{"opcode":1,"args":{"cmd":"id; cat /etc/shadow"}}` returned `ok:true`. Nothing
executed — `Describe` has no execution path — but the helper *accepted an
undeclared field*. A future refactor that starts reading `args.cmd` would find
attacker-supplied data already sitting there. Rejecting unknown keys is cheaper
than reasoning about that.

### 3.4 Paths are resolved by the kernel, inside a fixed root

Two independent layers, both required:

| layer | mechanism | catches | cannot catch |
|---|---|---|---|
| lexical | whitelist `[A-Za-z0-9._/-]`, no leading `/`, no `.`/`..` component, no NUL | metacharacters, obvious traversal | symlink TOCTOU |
| kernel | `openat2()` with `RESOLVE_BENEATH \| RESOLVE_NO_SYMLINKS \| RESOLVE_NO_MAGICLINKS` | symlink escapes, `/proc/self/root`-style magic links, races | — (it is the guarantee) |

The lexical layer exists for *error precision*, not for safety. It lets the log
say `path_invalid` (you used a character that is not in the alphabet) versus
`path_escape` (you tried to leave the root). The kernel layer is the actual
containment.

Measured, `T3-helper-rejections`: 8/8 escape attempts refused (`path_escape` ×8:
`../../etc/shadow`, `/etc/shadow`, `../etc/shadow`, `sub/../../etc/shadow`,
symlink-to-`/etc/shadow` absolute, symlink relative, symlink-to-`/root`,
symlink-to-`/etc`), 12/12 metacharacter paths refused, **0 escapes served**.

**Absolutely forbidden:** `open(caller_string)`, `canonicalize()` followed by
`open()`, `chroot`, and any check-then-use sequence on a path.

### 3.5 Sizes are capped before parsing

- `MAX_FRAME_BYTES` = 64 KiB per frame. Oversized frames are **drained to the
  next newline** and refused; they are never truncated into something valid.
- `DISCARD_CAP_BYTES` = 8 MiB. A frame that never terminates past this closes
  the connection.
- `MAX_ARG_BYTES` = 4096 per string argument.

Memory is bounded by the caps, not by what the peer sends. The drain is not
optional: without it the tail of an oversized frame is re-parsed as a fresh
request, which is a request-smuggling shape. That was a real defect in the
prototype (`REPORT.md` §6.1, defect 3).

## 4. Audit requirements

### 4.1 One line per request, accepted or refused

Every request produces exactly one JSON line, including every refusal. A
refusal without a record is a bug, not a policy. Measured: 2000 requests →
2000 `RequestServed` records, plus 1 `HelperStarted` and 100
`ConnectionClosed` (per-connection lifecycle), total 2101 lines.

Oversized frames were initially *not* audited. That was found by this
experiment's own completeness check and is now a fixed invariant.

### 4.2 Ordering is a mechanism, not a hope

- File opened `O_APPEND | O_CREAT | O_WRONLY`, mode `0600`, never seeked,
  never truncated.
- The record is serialised to a single `Vec<u8>` ending in `\n` and written with
  one `write_all` **inside the same mutex critical section that assigns the
  sequence number**.

`O_APPEND` alone gives atomic offsets but not ordering. Measured under
100 concurrent clients:

```
audit_lines=2101  malformed_lines=0
sequence_min=1  sequence_max=2101  sequence_duplicates=0
sequence_dense_and_in_file_order=True
```

The last line is the property that matters: sequence order **is** file order.

### 4.3 Recommended mode 0600, and its limit

`0600`, owned by the daemon's uid, in a `0700` directory. The daemon re-asserts
the mode with `fchmod` on open, so a previously world-readable file is corrected
rather than trusted.

**This protects against other users, not against the owning user.** The owner can
rewrite, truncate or delete the file. Measured status: `NOT TESTED` for any
tamper-resistance property. If tamper-evidence is required, the log must go to a
sink the writing process cannot rewrite (append-only file attribute on a
supporting filesystem, a separate-privilege collector, or an external endpoint).
Until then, do not describe the audit log as tamper-proof.

### 4.4 What each line must contain

Reuse the envelope from `docs/00-phase0-protocol.md` §2, plus:

| field | purpose |
|---|---|
| `sequence` | dense, monotonic, matches file order |
| `event_id` | uuid v4 |
| `ts_wall`, `ts_mono_ns` | wall clock for humans, monotonic for ordering |
| `source` | `"policy"` for helper-originated records |
| `type` | `RequestServed` / `RequestRejected` / `ConnectionRejected` / `ConnectionClosed` / `HelperStarted` / `HelperStopped` |
| `payload.peer_uid` | the authorisation key |
| `payload.peer_pid`, `payload.peer_starttime_at_connect` | **attribution only** |
| `payload.opcode`, `payload.code` | what was asked, why it was refused |
| `payload.request_bytes` | for size-abuse detection |
| `evidence_status` | `observed` for anything the kernel reported |

`peer_starttime_at_connect` is named that way on purpose: it is the value
observed at connect time, and it may no longer describe the process. Do not
rename it to `peer_starttime`.

## 5. Hard constraints on any privileged helper

Each is backed by a measurement. A proposed helper that violates one is rejected
on the basis of this document, not on the basis of taste.

1. **`pid` from `SO_PEERCRED` is never an authorisation input.** Authorise on
   `uid` and a server-minted per-connection token. `pid + starttime` is
   attribution only. Never map `SO_PEERCRED.pid` to `/proc/<pid>` for a
   permission decision. *(§2.2, §2.3; `T1-peercred`)*
2. **The input is data, never a command.** Closed numeric opcode table, strict
   per-opcode argument allowlist, no field naming a program/shell/interpreter/
   syscall, no `eval`, no templates. *(§3.1–3.3; `T6-no-exec`,
   `execve_lines_after_startup=0`)*
3. **Every path is kernel-resolved inside a fixed root** with
   `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS)`, plus a
   lexical whitelist for error precision. No `open()` on a caller string, no
   `chroot`, no check-then-use. *(§3.4; 8/8 escapes refused, 0 served)*
4. **Every request, accepted or refused, writes exactly one audit line**, with
   the sequence number assigned in the write's critical section.
   *(§4.1–4.4; 2101/2101 lines, dense, in order)*
5. **`PR_SET_NO_NEW_PRIVS` at startup and before every request**, and the helper
   refuses to start if it cannot be set. Measured effect: `passwd -S USER`
   returns the full shadow status field; the same command under
   `--no-new-privs` returns only `USER P`. The setuid gain is suppressed by the
   kernel, not refused by the file mode. *(§4.6 of `REPORT.md`)*

Operational corollaries (design choices, not measurements):

- Socket `0600` in a directory `0700`, owner = the daemon's uid.
- The helper never reads `/etc`, never writes outside its configured root, and
  never invokes another program.
- The helper logs its own capability state and `no_new_privs` status at startup,
  so "what was it actually running as" is answerable from the log alone.

## 6. Explicitly out of scope

Refusing to build these is part of the boundary, not an omission.

### 6.1 Never

- **Arbitrary command execution**, in any form: no `sh -c`, no `system`, no
  "run this script" opcode, no plugin that is a program, no shell-string
  argument, no `env`/`PATH`-resolved program name.
- **Arbitrary file read or write.** Only paths under a configured root, only via
  `openat2` with the three `RESOLVE_*` flags.
- **A general-purpose privileged broker.** A helper that can be extended with new
  effects at configuration time is a root shell with extra steps. New opcodes are
  a protocol change with review, not a config entry.
- **Trusting `pid` for access control.** See §2.2.
- **`setuid` binaries under our control.** The helper, if built, acquires
  privilege by an explicit, auditable mechanism (a systemd unit with a capability
  set, or a narrowly scoped file capability), not by a setuid bit on a binary in
  a user-writable directory.
- **Reading other users' process memory, environment, or open files.** Measured
  DENIED as a plain user and not a goal.
- **Modifying `/etc`, `/boot`, `/usr`, or any system directory.** This experiment
  never did, and a future helper must not either.

### 6.2 Not yet designed (and therefore not claimed)

| gap | why it matters | status |
|---|---|---|
| Per-connection capability token | the only sound substitute for `pid`-based identity (§2.4) | **designed, NOT TESTED** |
| Half-frame read timeout | a peer can hold a thread and an fd indefinitely (`T7-half-frame`) | **defect open** |
| Connection/worker caps | bounds the cost of the above | **NOT TESTED** |
| Tamper-evident audit sink | `0600` protects against other users, not the owner | **NOT TESTED** |
| `SCM_CREDENTIALS` per-message identity | might solve liveness + identity together | **NOT TESTED** |
| `pidfd`-based identity anchoring | closes the reuse hole but needs ptrace-level rights | **NOT TESTED** |

### 6.3 Phase 1 decision

Phase 1 is a **user daemon with no privileged helper**. Every capability it needs
was measured ALLOWED as uid 1000: `/proc` reads (including other users'
`stat`/`cmdline`, so process enumeration works partially), inotify on owned
directories, `AF_UNIX` sockets, sqlite writes, hardlink/rename. Every DENIED
capability (`/etc/shadow`, `/proc/<pid>/environ`, inotify on `/root`, btrfs
snapshot, mount) is either unnecessary for Phase 1 or a `declared`-quality
feature that can be deferred.

A privileged helper is introduced at **Phase 3 at the earliest**, and only when
all of the following hold:

1. A named capability from the inventory is provably needed and cannot be
   obtained unprivileged.
2. The half-frame stall is fixed and connection limits exist.
3. The audit sink question is answered.
4. This document's constraints 1–5 are accepted unchanged.

Until then, no helper exists — setuid or otherwise.
